# Coordinación de Gennie Web

## Objetivo acordado

Un único perfil persistente, con uso exclusivo alternado entre Chromium visible y headless. Las tareas reutilizan el proceso headless y reciben pestañas propias; el perfil visible no se utiliza para automatizar. Al necesitar headless se permite cerrar la ventana visible y reabrirla al terminar si estaba abierta. Antes de cambiar de modo se protegen las acciones, diálogos y descargas pendientes detectables. Los formularios sin guardar no están garantizados por Chromium.

## Estado observado

`apps/browser` posee un solo proceso Node, un contexto persistente, una selección global de pestaña y un controlador compartido y un transporte IPC que identifica y enruta peticiones concurrentes. Las herramientas MCP del chat reciben un ámbito atribuido por el host y usan pestañas propias en ese contexto; el constructor reserva una pestaña y solicita headless antes de crearla. `plugins::resume` solicita explícitamente el cambio a headless antes de encolar. El contexto headless se cierra tras diez minutos sin llamadas si no hay tareas del constructor, descargas, acciones o diálogos pendientes; el worker sigue vivo. El proceso Node ordena por ámbito y permite operaciones simultáneas de ámbitos distintos; las respuestas incluyen identificador. El contexto de invocación LLM contiene el hilo durante `speak_stream_reply` y se limpia al finalizar el comando; bootstrap ya lo usa para atribuir otras herramientas. El constructor, en cambio, crea un servidor MCP propio por trabajo y dispone del identificador de ese trabajo. Bootstrap inyecta el hilo en las herramientas del chat y solicita liberar su ámbito al terminar el turno; el constructor conserva su propia pestaña. La selección visual del historial no participa.

Una cancelación de una petición enviada deja de esperar su respuesta; el proceso compartido permanece disponible si su transporte sigue sano y el efecto puede ser incierto. El diario de ejecución web conserva los resultados inciertos. Multiplexar sin cambiar ese comportamiento podría cerrar las tareas de otros consumidores o atribuir una respuesta a la petición equivocada; el transporte y la gestión de resultados inciertos deben cambiar conjuntamente.

## Contrato de implementación

- Browser conserva la propiedad del perfil y coordina estados cerrado, visible, transición y headless; no crear una app nueva sin necesidad demostrada. La transición visible→headless recuerda la apertura previa, verifica actividad detectable y espera el cierre real antes de reutilizar el perfil. La restauración se ejecuta cuando terminan todas las reservas, incluso ante error o cancelación, y no abre una ventana que el usuario no tenía abierta. Una solicitud visible durante actividad headless debe esperar o informar que está ocupada, sin interrumpirla.
- Asignar identidades de ámbito desde el origen confiable en bootstrap o desde el trabajo del constructor; no confiar en que el modelo proporcione una identidad de otro chat. Cada ámbito recibe su propia pestaña y selección; comprobar pertenencia en cada operación, incluidas pestañas, diálogos y referencias. Liberar únicamente recursos propios; los identificadores deben invalidarse al cambiar de generación.
- Permitir peticiones concurrentes a pestañas distintas sin lanzar un navegador por petición. Multiplexar solicitudes/respuestas del proceso Node con IDs y controlar serialización por pestaña y operaciones globales. Mantener límites, cancelación y resultado incierto sin repetir efectos; evitar que cancelar una tarea retire el proceso de otra. El diario web y sus reservas previas al efecto deben conservarse.
- Cerrar el proceso headless tras un plazo de inactividad medido desde la última operación finalizada, sin cerrar mientras haya reservas, acciones, diálogos o descargas activas. El temporizador y el cierre pertenecen al controlador y deben terminar durante shutdown. Definir un valor inicial y exponer configuración solo si resulta necesaria.
- Preservar explícitamente las ventanas/pestañas restaurables del usuario y comprobar que el arranque headless no las modifique. La restauración de Chromium no garantiza formularios, sessionStorage ni que un sitio mantenga su sesión. No registrar cookies ni datos de usuario.

## Verificación necesaria

Pruebas con runtimes ficticios para asignación y aislamiento de ámbitos, solicitudes simultáneas, cancelación independiente, generaciones, temporizador, descargas y fallos de transición. Una prueba real aislada con perfil temporal y servidor local debe comprobar cookies, alternancia, restauración de pestañas, bloqueo por actividad pendiente y cierre por inactividad. Verificar además integración de las herramientas del chat, constructor, recetas y cierre global, sin alterar el perfil real del usuario. Documentar los resultados y sus límites; no declarar implementado hasta completar estas comprobaciones.


## Evidencia actual

Las sondas con Chromium real y perfiles temporales comprueban cookies, historial, ventana visible, perfil exclusivo, ámbitos concurrentes, cancelación independiente, recuperación tras interrupción y salida inesperada de Chromium, ventana de reutilización, avisos y limpieza aplazada con descarga y diálogo, sin cerrar los demás ámbitos. La transición rechaza una segunda instancia durante la reserva del perfil y conserva una ventana de 1,5 s para reutilizar Chromium entre tareas consecutivas. La prueba integrada Rust–Node–Chromium usa un servidor loopback temporal. Se ejecutaron `cargo test --workspace --locked`, Clippy del workspace, formato e invariantes; la sonda real de recetas verificó una receta de prueba. La primera ejecución de esta última falló técnicamente sin diagnóstico recogido y la repetición aislada pasó. No se usaron cuentas personales ni se verificó una sesión completa con proveedor real o el runner Flutter recompilado. Formularios sin guardar, sessionStorage y la permanencia de una autenticación remota no están garantizados.
