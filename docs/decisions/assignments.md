# D-025 — Registro de encargos y MCP modular

2026-10-25. Alcance solicitado: registrar planes mediante la conversación y editarlos en Flutter. No se implementan ejecución programada, cron, entrega de avisos, memoria, Gmail ni plugins nuevos.

## Propiedad y composición

`apps/assignments` posee `AssignmentsModule`, `Store`, documentos tipados, validación, herramientas y las migraciones `0001_events.sql` (histórica e inmutable) y `0002_assignments.sql` (renombrado de tabla). Se registra explícitamente y migra incluso apagado. No depende de llm ni presence. `kernel/mcp` es una biblioteca de protocolo/transporte, no una app registrada ni propietaria de tablas. Cada app puede aportar herramientas mediante `Tool`; bootstrap decide cuáles registrar según los módulos activos. Kernel no importa apps. Un módulo desactivado no publica sus herramientas y la API rechaza guardados.

Bootstrap construye un único Store con un clon de la conexión SQLite compartida. Después de migrar, inicia el host MCP y configura LLM antes de arrancar su worker. El proceso Codex recibe automáticamente `mcp_servers.gennie` mediante overrides `-c` en cada creación del app-server; no hay instalación manual, cambios de configuración global, credenciales nuevas ni copia de tokens. El servidor es requerido y sus herramientas locales están aprobadas en esa sesión. Los permisos de archivos/comandos de Codex son independientes del registro de datos de la app. La configuración de títulos efímeros desactiva expresamente este MCP. Al abrir el escritorio se encola Connect en el worker LLM, sin esperar al primer mensaje ni bloquear Flutter. Antes de publicar Connected se consulta mcpServerStatus/list para ese hilo y se exige que estén todas las herramientas registradas del host. Un fallo se comunica mediante el estado/error existente y Conectar permite reintentar. No se envía turn/start durante esta preparación.

La documentación oficial de [MCP en Codex](https://developers.openai.com/codex/mcp) describe stdio, servidores requeridos y políticas por servidor. El helper Rust `gennie --mcp <socket>` adapta stdio al socket Unix privado del host; no abre SQLite. Directorio efímero 0700 y socket 0600, sin puerto TCP/HTTP. Máximo 16 conexiones, líneas limitadas a 128 KiB y workers propios unidos al cerrar. Cada cliente espera lectura en bloques de 50 ms y escritura con timeout; el coordinador cierra llm, host MCP y después DB. Se permiten conexiones simultáneas para varios hilos del app-server. No hay persistencia de endpoints ni scheduler.

## Datos e invariantes

`assignments` guarda id, request_key única, revisión, documento JSON validado y fechas UTC. El documento incluye título, descripción, contexto/motivo opcionales, tipo (`one_time`, `recurring`, `goal`), prioridad, estado del registro, zona IANA, aviso puntual o recurrencia, preparación y aplicaciones necesarias. La escritura parametrizada, lectura del resultado y confirmación comparten transacción. Una clave repetida con el mismo documento devuelve el registro existente; con otros datos falla. Actualizar requiere revisión vigente para impedir sobrescribir ediciones concurrentes. La señal de revisión cambia después del commit y el coordinador refresca Flutter, también tras llamadas MCP.

La primera versión admite aviso puntual en ISO UTC, recurrencia diaria/semanal con HH:mm y días ISO 1–7, y objetivos con fecha límite opcional. La zona se valida contra un archivo TZif del sistema; las fechas contra su normalización SQLite. No se aceptan fechas imposibles ni campos desconocidos. La recurrencia conserva hora local y zona para que el futuro ejecutor aplique reglas de horario de verano; todavía no se calculan próximas ocurrencias ni se decide cómo resolver horas ambiguas/inexistentes. El editor puntual usa fecha/hora local del sistema y convierte el instante a UTC. La cadencia de preparación es opcional, en minutos, con justificación y pasos; nunca cambia la hora de aviso ni genera notificaciones.

Cada aplicación registra nombre, desktop/web y URL opcional. Al no existir catálogo de plugins conectado, el backend fuerza `plugin_available=false` y `manual_required=true`, aunque el agente afirme lo contrario. Es metadato de planificación, no una integración ni autorización para acceder a cuentas. Los estados activo/pausado/completado/cancelado describen el encargo; no prueban que se haya trabajado en él.

## Conversación y escritorio

Las herramientas son `assignments_list`, `assignments_get`, `assignments_create` y `assignments_update`. List devuelve resúmenes paginados (20 por defecto, máximo 50), fecha UTC y zona del sistema; get devuelve documento completo. Las instrucciones piden consultar la referencia horaria antes de crear, separar preparación/aviso, justificar cadencia según importancia y preguntar brevemente por datos indispensables no inferibles. El motivo puede inferirse dejando constancia en contexto o permanecer vacío. Un prompt guía al modelo; no garantiza cómo formulará cada pregunta. El agente solo debe confirmar tras éxito y resumir lo registrado, sin añadir advertencias automáticas sobre implementación. Los metadatos internos no prueban ejecución ni conexión; las preguntas explícitas sobre capacidad real y los fallos concretos se responden con claridad.

Flutter consume el puente regenerado. Encargos tiene navegación propia, lista/búsqueda de los 100 registros más recientes y editor en el mismo panel. Comparte AppSidebar y ancho redimensionable con Historial/Plugins, manteniendo lista/editor juntos hasta el mínimo de ventana de 640 × 420. Búsqueda, filas y estados vacíos usan los mismos componentes del escritorio. Permite crear/editar planes, aplicaciones, preparación y estado; conserva borrador tras error y clave de creación al reintentar, bloquea guardado pendiente y detecta conflictos de revisión. No realiza SQL ni inicia procesos. No hay eliminación física, acceso a memoria ni ejecución de acciones en esta pantalla.
