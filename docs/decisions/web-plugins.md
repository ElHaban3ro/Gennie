# D-027 — Plugins web personalizados

2026-10-26. [Plan y constructor aislado](../plans/web-plugins.md). Bloques de consulta y programables reutilizables desde MCP/Rust, constructor Codex aislado bajo demanda y pantalla de Plugins con prueba manual de funciones. La ejecución periódica queda expresamente fuera del alcance.

## Contrato del constructor: interfaz oficial

El constructor descubre recorridos de la interfaz oficial y los convierte en funciones reutilizables comprobadas. DOM/accesibilidad y capturas visuales se complementan; los identificadores y selectores observados sostienen la ejecución. Una API externa es una alternativa u optimización cuando procede, no una dependencia que se añade al encargo. La unidad que agrupa la interfaz se describe fielmente; no se exige desagruparla con una API si el usuario no lo pidió ni se afirma que una lista de conversaciones sea una enumeración de mensajes individuales.

Las instrucciones separan resultado, ciclo de recuperación, comunicación y protocolo de herramientas. El constructor actúa como ingeniero autónomo, resolutivo y autocrítico: mantiene capacidades pendientes/comprobadas y el registro de lo probado, lo aprendido y el próximo experimento. Cada intento responde a una incertidumbre concreta; tras cambiar la vista vuelve a observar y, si una vía falla, cambia de hipótesis o recorrido en vez de repetir resultados equivalentes. Completar incluye implementar, ejecutar, inspeccionar y corregir. La concisión limita los mensajes, no el trabajo. Se conservan permisos y la prohibición de repetir escrituras inciertas.

El asistente que delega debe incluir en objective la petición literal pertinente, el resultado/restricciones acordados y, separados, los hallazgos previos por revisar. Esta estructura vive en el texto del objetivo, sin migración ni extracción automática desde el historial. Un bloqueo anterior no se convierte en requisito; el constructor contrasta la interpretación con la petición disponible y aclara contradicciones materiales. Ante una aclaración que cambia el objetivo se solicita una construcción nueva para el mismo plugin, con clave nueva; el reintento con retry_of conserva el objetivo anterior. Estas instrucciones no corrigen retrospectivamente trabajos o mensajes guardados ni garantizan la interpretación del modelo.

La revisión de instrucciones se basa en [autonomía de GPT-6](https://developers.openai.com/api/docs/guides/latest-model), [simplificación de prompts](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra), [objetivos persistentes](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex) y [observación de interfaces](https://developers.openai.com/api/docs/guides/tools-computer-use). Se adaptan criterios de estas guías, no se cambia el modelo/esfuerzo ni se afirma transferencia automática de sus resultados a la configuración del usuario.

El constructor dispone de browser_screenshot sobre su pestaña propia, con la misma conversión MCP de imagen que el navegador general: los píxeles viajan en content=image y los metadatos en structuredContent. No se entregan imágenes como texto base64 al contexto. Las capturas del constructor viajan por MCP sin generar archivos de exportación en browser/artifacts; las capturas explícitas del navegador general siguen conservando su archivo. No se usa el perfil personal ni se añaden capturas a SQLite. Esto no afirma que el proveedor o el historial técnico de Codex no conserven el contenido recibido. El modelo debe emitir los bloques de imagen cuando orquesta llamadas mediante exec.

plugin_build_findings lista avances y permite leer candidatos anteriores del mismo plugin/origen/chat. No ejecuta sus funciones, no hereda verificaciones y exige revisar el código contra la autorización vigente. Permite recuperar hallazgos ausentes del último candidato publicado sin rescatar funciones fuera del alcance actual. La consulta usa el catálogo de trabajos ya existente, sin migraciones ni copias nuevas de contenido web.

plugin_build_investigate fija un ID estable de capability y una hipótesis técnica antes de explorar. Cada resultado UI genera un build_observation.id del host con capacidad, hipótesis, turno y estado entregado/fallido; se conserva en memoria solo procedencia y huellas del contenido, no una copia de la pantalla. Las huellas normalizan IDs efímeros para detectar lecturas repetidas incluso si se cambia el nombre de la hipótesis. API/request/network y pruebas de candidato no constituyen observación UI para confirmar una detención.

Para aceptar exhausted_alternatives o permission_required, observation_ids debe citar evidencia real de esa capacidad y candidato: DOM entregado, captura entregada o fallo visual identificado, y exploración de controles lograda. Un timeout/error no equivale a inspección lograda y Busy no genera evidencia. Una captura fallida permite diagnosticar el canal y continuar por DOM, no afirmar que se vio la pantalla. La revisión posterior necesita observación UI pertinente, entregada y nueva; duplicados, errores o datos de otra capacidad no bastan. Guardar candidato invalida IDs y propuesta anteriores. El host acredita procedencia y pertinencia declarada, no comprensión visual ni agotamiento semántico completo de alternativas.

## Propiedad e interfaz

`apps/browser` conserva la propiedad del navegador y añade recetas en `browser/plugins/<id>.json`. D-044 añade únicamente browser_web_attempts para reservas/recuperación/revisión; las recetas continúan en archivos, sin HTTP entrante u otro navegador por plugin. `apps/plugins` posee el constructor y sus tablas; reutiliza dependencias ya fijadas en el workspace. `plugins.mjs` concentra validación/persistencia/ejecución; `worker.mjs` compone el mismo ejecutor que se importa en las sondas. El helper Rust embebe ambos archivos, sin necesitar fuentes JavaScript al distribuir la app.

MCP publica `browser_plugins` (list/get/save/delete), `browser_plugin_run` (verify/run) y `browser_network` (start/read/stop). `Controller::run_web_plugin` ofrece la misma ejecución verificada a consumidores Rust; es bloqueante y requiere worker. Bootstrap registra las herramientas mediante browser y plugins. FRB publica plugin_request para el catálogo, la construcción y pruebas manuales. Ejecutar y construir conservan el permiso de control de aplicaciones; el catálogo propio puede consultarse/editarse sin conceder control al navegador. El catálogo completo pasa de 21 a 24 herramientas.

Una receta tiene id/nombre/origen y una o más funciones, sin límite fijo de cantidad de funciones ni parámetros. Cada función define parámetros, ruta, query opcional, transporte y contrato de resultado. Conserva string/integer requeridos y admite descriptores type string/integer/number/boolean, label, description, required (true por defecto), enum y límites minLength/maxLength/minimum/maximum. Los opcionales ausentes no se rellenan; si una query depende de ellos se omite esa entrada, mientras que los parámetros de ruta siempre deben ser requeridos. Los argumentos de ruta se codifican; la query se construye mediante URLSearchParams. Se rechazan orígenes/rutas/propiedades desconocidos y parámetros de autenticación en query. El transporte program añade JavaScript suministrado por el constructor; puede usar Node y Patchright, incluidos headers y cuerpos cuando el objetivo lo requiera.

- Program: cuerpo JavaScript async con context, page, args y origin. Corre en el proceso Node del navegador, con sus permisos y acceso al perfil; no es un sandbox. Requiere los cuatro permisos de archivos, comandos y control de aplicaciones. Verificar ejecuta el código y puede producir efectos reales. Un fallo o resultado no conforme se informa como incierto, sin reintento automático.
- HTTP: GET sobre `context.request`, cookies compartidas, JSON, selección por JSON Pointer y proyección opcional de campos. Redirecciones manuales: solo mismo origen salvo reconocer una ruta de acceso configurada; no se sigue una redirección externa arbitraria.
- Página: pestaña temporal propia, navegación y extracción de texto/filas/campos CSS. `ready_selector` permite comprobar una lista cargada pero vacía. La pestaña se cierra al terminar. El filtro de rutas limita las solicitudes a GET/HEAD del origen y navegación a accesos configurados; no es una garantía de sandbox del navegador ni evita efectos que una web asocie a GET. Sitios que necesiten CDN, POST, service workers o tokens especiales pueden requerir una ampliación comprobada.

El resultado incluye status, plugin/función y revisión; data solo ante éxito. Se distinguen authentication_required, access_denied, site_changed, http_error, redirect_blocked, timeout, execution_failed, verification_required y revision_conflict. No se guardan respuestas, errores libres, cookies ni contraseñas en los registros del catálogo. La instrucción del agente exige comprobar el contenido semántico: validar tipo/campos y ejecutar sin fallo no demuestra por sí solo que la consulta responda al objetivo.

Los bloques `program` reciben `runtime` además de context/page/args/origin. `runtime.read(etapa, operación)` reintenta hasta tres veces únicamente timeouts y códigos conocidos de conexión. `runtime.action(etapa, acción, verificador)` consulta primero la poscondición; si falta ejecuta la escritura una sola vez y observa el resultado incluso tras una excepción. Repite hasta tres observaciones de lectura ante estados todavía no confirmados, sin repetir la escritura. Si el estado ya se cumple, informa already_satisfied. El verificador debe usar identidad estable y comprobar el efecto real: la desaparición de una fila por posición no prueba un archivo. Estas garantías pertenecen a la llamada al helper; el código que ejecuta efectos fuera de él sigue siendo responsabilidad del bloque. La primera verificación de escritura debe cubrir también una acción autorizada y su efecto, no solo un estado previo.

Un error programable conserva un diagnóstico de etapa técnica, fase, estado de la acción y código fijo, sin mensajes libres del sitio. Un fallo de cierre de la pestaña se informa por separado sin reemplazar el resultado de la acción. La construcción cubre capacidades reutilizables: la ausencia del programador periódico se explica separadamente y no bloquea por sí sola la publicación de un plugin cuyas funciones estén comprobadas. No se publica un candidato con funciones pendientes ni se activa periodicidad por esta distinción.

## Acceso solo cuando haga falta

Guardar/listar una receta no abre Chromium. La ejecución intenta contenido público o cookies existentes; abre headless bajo demanda si no hay contexto. Un 401 o la llegada a una ruta de acceso configurada y observada produce authentication_required. En página también puede usarse un login_selector observado. Un 403, un fallo de transporte o un contrato cambiado no se convierten en una petición de login.

Ante acceso necesario, el asistente abre Gennie Web visible y deja al usuario completar login/2FA; nunca pide credenciales en el chat. Al abrir visible desde headless se cierra primero el contexto propio y se reabre el mismo perfil, sin dos instancias concurrentes. Se rechaza la transición si hay descarga, acción o diálogo pendiente. Al reanudar una construcción, se cierra el contexto visible de Gennie Web y el constructor abre el mismo perfil en modo headless. La transición se rechaza si hay una pestaña de trabajo activa, descarga, acción o diálogo pendiente; el trabajo permanece sin reanudar. Cerrar el contexto puede descartar formularios sin guardar y otros datos efímeros; no garantiza que el sitio conserve la autenticación. Las demás llamadas en segundo plano reutilizan una instancia visible existente. No hay aislamiento por cuenta ni selección automática de cuentas: se comparte el perfil existente.

`login_url` sirve para indicar acceso al usuario; `login_urls` reconoce destinos observados, sin query/fragmento/credenciales. Tenerlas en el manifiesto no solicita acceso por anticipado. La caducidad se detecta al operar, no por un reloj artificial.

## Persistencia, límites y verificación

Guardar usa expected_revision=0 al crear y revisión vigente al editar. Cada edición incrementa revisión e invalida toda evidencia anterior. Una función requiere verify satisfactorio antes de run; verificar también realiza la consulta real. La evidencia contiene solo fecha ISO UTC y revisión por función. La receta queda preparada tras reinicio; la sesión puede haber caducado igualmente.

Catálogo de hasta 50 plugins activos; directorio 0700 y archivos 0600; nombres cerrados, rechazo de symlinks del directorio/archivo, tamaño máximo 128 KiB al leer y 64 KiB del manifiesto; cada bloque de código admite hasta 48.000 caracteres. Escritura temporal exclusiva y rename, sin sobrescribir rutas elegidas por el usuario. La edición directa sustituye la receta e invalida sus verificaciones. El constructor usa candidatos separados bajo browser/plugins/candidates/job_<id>; promoción comprueba todas las verificaciones y la revisión de origen. El borrado deja solo un marcador de id/revisión, sin manifiesto, para impedir sobrescrituras con revisiones antiguas al recrearlo.

HTTP: hasta cuatro redirecciones seguidas, cuerpo JSON hasta 1 MiB comprobado tras recibirlo y salida hasta 100.000 bytes. DOM: hasta 200 filas, texto hasta 2.000 caracteres por campo y salida hasta 100.000 bytes. Los límites de bytes no son límites de descarga previos a recibir la respuesta; DOM devuelve la proyección acotada y marca truncated al recortar filas/textos, sin prometer extracción completa. Presupuesto de operación 6,5 s para solicitudes/esperas; IPC de ejecución de plugin hasta 15 min, puente MCP hasta 15 min 15 s y cliente Codex 15 min 30 s, para que el navegador devuelva el error antes de que lo cierre el puente. Cierre y último recurso kill/wait conservan el mecanismo propietario del navegador.

La observación de red dura hasta 120 s y conserva las últimas 100 respuestas xhr/fetch/document del origen solicitado, con truncado explícito. Solo registra método, origen/ruta, nombres de query, status y content type; no captura headers, cuerpos ni valores de query. Es transitoria, no logs ni historial persistente. Las rutas pueden contener información del sitio y deben tratarse como datos de la tarea, no como instrucciones.

```json
{
  "id": "example_messages",
  "name": "Mensajes del sitio de ejemplo",
  "origin": "https://example.com",
  "functions": [{
    "name": "list_messages",
    "description": "Consultar mensajes posteriores a una fecha",
    "parameters": {"after": "string"},
    "transport": "http",
    "path": "/api/messages",
    "query": {"after": "{after}"},
    "result_type": "array",
    "result_pointer": "/messages",
    "fields": {"id": "/id", "subject": "/subject"}

```

Es un formato ilustrativo; no demuestra que example.com ni Gmail ofrezcan ese endpoint. Primero se observa la operación de consulta autorizada.

## Evidencia

Pruebas aisladas Node cubren contrato cerrado, rechazo de credenciales/código, conflictos y pérdida de verificación, resultados de autenticación/acceso/cambio de sitio, argumentos, errores sin filtrado y symlinks. La sonda `scripts/probes/web_plugins.mjs` usa Chromium real, sitio local y perfil temporal: HTTP y DOM, público sin login, acceso requerido, cookie de sesión, reapertura del perfil, caducidad remota simulada, observación sin valores de query, listas vacías y cierre de pestañas propias. No consulta cuentas personales ni valida Gmail, login/2FA físico o reparación autónoma.

Resultado de la entrega: 6 pruebas Node, 4 Rust de browser y 19 de llm correctas (5 externas omitidas); 32 comprobaciones reales del plugin, incluido el formato embebido en el helper, y las 71 operaciones previas del navegador. Clippy de browser/llm sin warnings, formato, invariantes y diff correctos. En esa entrega inicial no se reemplazó la aplicación abierta ni se desplegó.

## Constructor aislado, trabajos y chat de origen

`apps/plugins` es un AppModule explícito compuesto por bootstrap; depende de sus controladores inyectados, con orden opcional respecto de browser/llm/presence para permitir catálogo sin proveedor activo. Sus operaciones comprueban permisos y disponibilidad antes de crear trabajo. Posee `plugin_build_jobs` y `plugin_build_events` sobre la conexión SQLite compartida, sin acceder a tablas de otra app. Migra incluso apagado. Arrancar crea un worker serial sin inferencia ni navegador; solo una solicitud autorizada crea un trabajo. Hasta ocho trabajos vivos; las peticiones de Encargos pueden encolarse por plugin y solo una se ejecuta a la vez. No hay scheduler de consultas web.

MCP principal añade plugin_build_start y plugin_build_jobs (list/get/cancel/resume). El chat emisor se resuelve desde el hilo del turno LLM en curso mediante un trait inyectado; no lo suministra el modelo ni se consulta el chat seleccionado. Desde la pantalla Plugins se conserva el chat seleccionado al enviar la solicitud. request_key hace idempotente la creación para los mismos datos y chat.

Cada trabajo usa un Codex app-server y un hilo propios, con CLI home y workspace separados, instrucciones de ingeniería y autenticación ChatGPT según el mecanismo existente, sin copiar credenciales. No guarda el hilo en codex_conversation ni activa un chat de presence. El constructor usa los permisos de archivos, comandos y control de aplicaciones configurados, además de herramientas de navegador, candidato y reportes. La navegación de la pestaña se restringe al origen delegado. Las consultas GET/HEAD a servicios auxiliares HTTPS del mismo encargo admiten service_purpose y documentation_url pública como justificación técnica; se validan estructura, HTTPS y ausencia de credenciales, sin certificar semánticamente que el servicio esté relacionado. Esta ampliación permite observar una respuesta real de APIs que usan otro dominio, sin conceder OAuth ni cambiar la autorización de las acciones. Los datos de justificación se consumen en el constructor y no se envían al servicio. Las fuentes públicas se investigan mediante búsqueda nativa; las webs pueden redirigir o incluir recursos de otros orígenes, por lo que no se promete aislamiento de red completo del motor.

El constructor usa una pestaña propia sin cambiar la selección del navegador. Los métodos de creación/lectura/verificación de candidato no permiten escribir el plugin publicado. El candidato inicial de una actualización copia la versión vigente. Las funciones nuevas o modificadas requieren verificación; las exactamente idénticas pueden reutilizar evidencia vigente de la versión publicada, con source_revision explícita. El agente declara ready; el host vuelve a comprobar evidencia y revisión antes de promover en una llamada serial al worker. Cancelación/promoción se coordinan mediante una exclusión propia. Una edición concurrente produce conflicto y conserva el candidato.

Al volver a generar un trabajo bloqueado o cancelado, se registra explícitamente el trabajo de origen y se copia su manifiesto candidato al nuevo espacio aislado. Se exige que coincidan plugin, origen, objetivo, chat y revisión publicada; la copia invalida las verificaciones y requiere volver a comprobarlas antes de promover. Si no existe candidato anterior se informa y se investiga desde cero. El constructor investiga por separado las capacidades factibles aunque otra falte, dentro de la autorización. El transporte program permite implementar acciones reutilizables, además de investigar en la pestaña.

Cada construcción conserva un Goal nativo asociado a su hilo técnico con el objetivo y la autorización. El app-server inicia turnos automáticamente si el Goal queda activo; para evitar carreras con el controlador, Gennie lo registra en pausa y dirige explícitamente los turnos, con el objetivo presente en cada petición. Solo solicita estado completo después de promover el candidato verificado. Al reanudar se comprueba que el objetivo guardado coincida; no se crea un hilo conversacional ni se amplían permisos. La prueba local del protocolo sin cuenta confirmó creación, consulta y estados, pero no demuestra una construcción real con inferencia.

Cada petición explicita execution_state=running y que la pausa del Goal es técnica, no una orden del usuario; la continuación vigente prevalece sobre avisos históricos de pausa. Si tres turnos consecutivos terminan sin invocar herramientas locales del constructor, el host conserva hilo/candidato y programa una sesión nueva en cinco minutos con aviso por outbox. Una llamada local reinicia ese contador. No limita el total de turnos ni la duración de la construcción; tampoco detecta ciclos que sí llaman herramientas o demuestra ausencia de investigación mediante búsqueda nativa. Cancelación y otros estados aplicados durante un turno prevalecen sobre esta recuperación.

Incidente del 27 de octubre: entre 13:40 y 15:40 UTC el trabajo 17 produjo 1164 finales que reiteraban una pausa, con una sola llamada exec registrada. El hilo contenía mensajes internos de Goal paused. A las 15:40:23 UTC el proveedor registró una desconexión WebSocket por alcanzar 60 minutos; después el turno fue interrumpido. El motivo local exacto de esa última interrupción no se conservó, por lo que no se atribuye con certeza a ese aviso ni a un plazo del constructor.

La construcción no tiene plazo mínimo ni máximo. El constructor mantiene un inventario de capacidades comprobadas/pendientes, investiga documentación pública mediante la búsqueda web nativa habilitada y contrasta alternativas con la web real. Que falte implementar o verificar una función, una cobertura parcial o un fallo recuperable no es una condición terminal. Los límites históricos almacenados no detienen ni impiden reanudar un trabajo. No se ha implementado un programador de encargos.

Los reportes blocked/waiting_user son propuestas, no transiciones directas. El host clasifica blocker.kind: work_remaining y recoverable_failure devuelven continue y mantienen running; user_action_required, permission_required y exhausted_alternatives necesitan impedimento observado y condición/intervención concreta. Agotar alternativas exige describir al menos dos vías distintas y aportar fuentes públicas/hallazgos de investigación, o explicar por qué investigar no está disponible. El host comprueba estructura y URLs, no certifica que las fuentes declaradas fueran consultadas ni que los argumentos sean semánticamente ciertos.

Una propuesta terminal identifica una sola capability estable; exhausted_alternatives exige además required_outcome y outcome_status=unmet. Un efecto ya satisfecho, no solicitado o ambiguo devuelve continue para verificar, mantener el alcance o pedir aclaración, sin declarar imposibilidad por la ausencia de un botón. Una propuesta válida devuelve review_required sin publicar un bloqueo ni cambiar el estado. En el siguiente turno se inyecta una revisión crítica; para confirmar una detención de la misma capacidad y tipo se exige además evidencia UI nueva del criterio en ese turno. El objetivo del trabajo es inmutable y el ID de capacidad conserva identidad aunque se parafrasee required_outcome; cambiar la redacción no reinicia por sí solo la revisión. Leer o probar el candidato no sustituye la evidencia de inspección UI para aceptar un bloqueo. Guardar con éxito una nueva revisión invalida la propuesta anterior; un impedimento distinto necesita una revisión nueva, aunque tenga el mismo tipo. El modelo debe intentar refutar el bloqueo y continuar cuando haya una vía viable; una declaración repetida en el mismo turno no puede cerrar. La revisión vive en memoria por construcción: al reanudar/reintentar se exige de nuevo, sin migraciones ni reactivación automática de trabajos ya bloqueados. El host no incorpora un segundo modelo y esta revisión no garantiza que nunca haya un bloqueo mal clasificado.

El presupuesto de 80 llamadas se renueva por turno y nunca justifica bloquear: los reportes de detención se devuelven como continue al agotarlo, y el siguiente turno recibe un presupuesto nuevo. authentication_required de una prueba se devuelve al constructor sin pausar automáticamente: debe distinguir una vía opcional de un acceso imprescindible a la interfaz. Si necesita intervención humana, propone waiting_user con la condición observada y conserva el flujo de login/2FA en la ventana. Se mantienen cancelación, permisos, reintentos estructurados del proveedor y prohibición de repetir escrituras inciertas.

Los turnos internos continúan sin plazo ni límite por número de intentos; se conservan los límites por herramienta y reporte. Los fallos transitorios de comunicación identificados por Codex se anuncian en el chat de origen y se reprograman cinco minutos después; el candidato y el reintento pendiente persisten y se reintentan al abrir Gennie. El reintento revisa el historial y evita repetir acciones de resultado incierto. Errores no identificados como transitorios y conflictos de revisión se informan como interrupción. El cierre solicita cancelación, mata/espera el grupo de procesos propio y une workers antes de cerrar MCP/SQLite. Las operaciones de navegador conservan su plazo IPC (hasta 15 min para plugins); no se promete cancelación instantánea de una consulta en curso.

La sesión técnica comprueba entre turnos si su host MCP conserva clientes conectados, también antes de promover. Si el helper desconectó, deja de generar turnos sobre ese canal y programa un reintento a cinco minutos con un aviso propio: conexión con herramientas de Gennie perdida, no error atribuido a OpenAI. Reutiliza retry_at/outbox y el hilo/candidato persistidos, sin migración. El siguiente intento crea servidor y proceso técnico nuevos y comprueba efectos anteriores antes de repetir operaciones. La señal observa conexiones, no salud semántica ni un bloqueo dentro de un turno aún abierto; no es un watchdog temporal.

El código closed del navegador se conserva como ClosedPageError en el controlador Rust. Si afecta a la pestaña acotada del constructor, plugins programa recuperación con una pestaña nueva y conserva hilo/candidato; no repite la acción fallida ni adopta pestañas del usuario. El siguiente intento descarta las referencias UI anteriores. Los reportes de progreso no tienen un tope acumulado por trabajo: el antiguo rechazo tras 200 eventos ocultaba avances posteriores en construcciones largas. La lectura de los últimos 100 eventos sigue siendo una ventana de presentación, sin impedir guardar otros nuevos.

Incidente inspeccionado sin reejecutar Gmail: el candidato del trabajo 17 guardó verificación a las 03:54:20 UTC y la llamada recibió Transport closed a las 03:54:21 UTC; después se repitieron cientos de turnos sin avances visibles. Al crear o editar un encargo web desde el chat, el commit de assignments solicita un trabajo por fuente: si existe un plugin del origen, el constructor revisa y adapta su candidato; si no, prepara uno nuevo. Al abrir el escritorio, el worker de plugins revisa todas las páginas de encargos activos y cada una de sus fuentes. La cancelación sin plugin publicado oculta la fila de la lista, sin borrar trabajos, eventos ni mensajes. Si hay un plugin publicado, su ficha permanece en la lista.

Una construcción completada sin un plugin publicado conocido no crea una fila propia: el historial se conserva, pero eliminar el plugin no lo hace reaparecer como trabajo terminado. Si el catálogo está ocupado en la primera carga se espera a conocer el plugin publicado; los trabajos pendientes o bloqueados siguen visibles sin publicación. Tras confirmar una eliminación se retira la fila también si el catálogo está ocupado; una consulta iniciada antes de eliminar no puede restaurar sus datos y se repite con el estado actual.

Eliminar un plugin también cancela sus trabajos bloqueados, al igual que los pendientes, para que no vuelvan a presentarse como una construcción activa tras retirar la versión publicada. Se conservan el trabajo y sus eventos; una eliminación rechazada por conflicto no modifica su estado.


El catálogo entrega los trabajos y sus hitos desde SQLite aunque el navegador esté ocupado o falle al leer los plugins publicados. catalogue_status distingue ready/busy/unavailable; con metadata no disponible, plugins=null evita afirmar que el catálogo está vacío y catalogue_error conserva el fallo visible. La UI mantiene los registros que ya conocía y reintenta su lectura cada dos segundos mientras esté montada; busy se presenta como actividad temporal, sin una falsa alarma de fallo de construcción. La primera carga muestra los trabajos sin esperar el catálogo y recupera la metadata al estar disponible. No se cambia la exclusión del navegador ni se repiten acciones web.

Una declaración ready solo puede promover tras terminar correctamente el turno. Guardar una revisión candidata nueva retira la declaración ready anterior y requiere declararla de nuevo tras verificarla. Esto protege el orden de eventos y no certifica por sí solo cobertura semántica del objetivo.

Recuperación al arrancar: el proveedor de ajustes inyectado al constructor aplica los permisos guardados al Controller del navegador antes de devolverlos. Comparte la misma composición que refresh_controls; así un trabajo con retry_at no intenta crear su pestaña antes de la primera actualización de la UI. No habilita permisos ausentes ni inicia otro perfil.

La reutilización de evidencia exige id/origen iguales, función serializada idéntica y prueba de la revisión publicada vigente. No hereda de otros candidatos ni de funciones modificadas/nuevas sin prueba. La promoción vuelve a leer la revisión publicada y rechaza conflictos antes de heredar. Evita repetir escrituras no autorizadas al ampliar un plugin de solo lectura. El constructor espera entre turnos si browser indica una operación ocupada; sigue comprobando cancelación y no consume intentos mientras espera.


## Datos faltantes y uso puntual — 2026-10-28

Las funciones publicadas se usan desde el chat sin crear un Encargo. El bot consulta el contrato, conserva los datos acordados y pide el principal dato indispensable, sin mandar al constructor un problema de entrada. Un destinatario ambiguo necesita aclaración; un permiso técnico o una función verificada no autoriza efectos. Las instrucciones del bot/constructor explicitan estos límites y los opcionales ausentes; no hay elección de destinatario por coincidencia de palabras en el host.

Antes de obtener contexto del navegador o ejecutar código, el ejecutor valida tipos, límites, elecciones y campos extra. input_required/invalid_arguments incluye executed=false y descriptores/razones, sin copiar los valores recibidos. No elimina evidencia vigente por un verify que no llegó a ejecutar. Los argumentos de una ruta siguen codificados; los opcionales ausentes se omiten de query. Formatos guardados anteriores se leen sin reescritura/migración ni pérdida de verificación. El esquema MCP y el constructor comparten el contrato ampliado.

Evidencia: 22 pruebas Node, diez Rust de browser, las suites llm/plugins/bootstrap afectadas y once casos nuevos de formulario (seis combinaciones visuales). Contraste medido de error y acción de ejecutar: mínimo 5,92:1, requisito 4,5:1, ambos temas y texto al 150 %. La sonda Chromium propia pasó 38 comprobaciones, incluido no abrir contexto ni producir efectos ante dato requerido ausente, completar después y ejecutar el formato embebido en el helper. Perfil/sitio/puerto temporales cerrados, sin cuentas personales.
