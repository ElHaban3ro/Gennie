# SQLite y migraciones

Propietario: kernel/db abre y comparte la conexión; bootstrap la crea una vez. Adaptación deliberada de los patrones PostgreSQL del prompt a SQLite local. No pool artificial: Arc/Mutex serializa una conexión. Apps no abren otra ni cargan ruta del entorno. Foreign keys ON, WAL y synchronous FULL; busy timeout configurable 1..5000 ms. No hay TTL/min/max de pool inaplicables a una sola conexión.

## Propiedad y operaciones
bootstrap posee modules; presence posee presence_preferences y presence_appearance. Repositorio de app concentra SQL parametrizado. Transacciones se abren y cierran por operación; no esperar UI/red con lock o transacción tomada. Configuración persistida de UI no es datos de negocio y no exige auditoría por defecto. Diseñar auditoría antes de acciones futuras de administración/sistema que la requieran; cambio y registro juntos.

## Migraciones
transcription posee transcription_preferences. La migración 0002 añade microphone_name opcional y amplía unload_seconds a 600, llevando el tiempo existente a 10 minutos por petición explícita. Conserva los demás ajustes y el historial de 0001. La 0003 fija bubble_seconds DEFAULT 15 y convierte los valores de 5 a 15, preservando otros tiempos, micrófono y demás preferencias. Mantiene el updated_at de las filas cuyo valor no cambia; las migraciones anteriores siguen inmutables.

SQL embebido desde migrations por módulo, versiones positivas y estrictamente ascendentes. Historial `_soc_migrations_<module>` (identidad persistida conservada tras el cambio de nombre a Gennie) con SHA-256 de bytes, versión y UTC. Nombre de módulo validado sin normalización ambigua. BEGIN IMMEDIATE protege migración y historial juntos; todo el conjunto de nuevas migraciones del módulo hace commit o rollback. No añadir BEGIN/COMMIT ni pragmas que rompan transacción dentro del SQL. Detectar checksum cambiado, historia ausente del binario y nuevas versiones insertadas hacia atrás.

Una migración aplicada es inmutable byte por byte: espacios/comentarios también. Correcciones en nueva versión. No DDL desde interacción o activación. Migrar módulos compilados incluso apagados según orden del registro. Revertir binario no está soportado si falta historia; no eliminar checksums para forzarlo. Para rollback compatible diseñar expansión/retirada y tests antes de prometer soporte.

## Cierre y datos locales

D-040: para ensayar una migración histórica, abrir el origen solo con mode=ro/query_only y obtener una copia coherente mediante SQLite Backup. Solo la copia cambia selección de módulos y se migra. Comparar columnas/filas previas, historia/checksums, claves, identidad y contenido sin publicarlo; controlar nuevas columnas y comprobar reapertura/recuperación. Usar conexiones cerradas, directorio privado y retirada de copias sensibles al terminar, salvo conservación solicitada. El informe agregado no sustituye un respaldo nuevo antes de actualizar datos reales con autorización.
Worker termina antes de DB.close; clones quedan cerrados juntos. No borrar DB para solucionar bugs sin autorización explícita. WAL implica conservar archivo principal y sidecars al copiar mientras hay proceso abierto; hacer backup después de cierre o mediante API diseñada. Primera base no sincroniza ni cifra datos. Pruebas ejecutan migraciones/escrituras solo en memoria o rutas temporales propias, nunca sobre data/gennie.sqlite3 o la base del usuario. El origen real solo se admite en lectura para obtener la copia coherente de un ensayo autorizado como D-040; no arrancar módulos sobre él. Cambios de SQL requieren atomicidad, reapertura, inmutabilidad, namespaces y selección conservada. Ver testing.

## Construcción de plugins

`plugins` posee plugin_build_jobs y plugin_build_events (migración 0001), con origen de chat fijo, request_key idempotente, revisión base y estado; los campos históricos de tiempo se conservan por compatibilidad y no limitan la construcción. Cambio e hito se confirman juntos. Su outbox entrega mediante un trait inyectado, sin consultar tablas de presence. 0011 de presence conserva los recibos históricos; las entregas nuevas atraviesan el inbox del bot y 0016, según D-029. Las migraciones anteriores no cambian. No mantener SQLite bloqueado durante Codex o navegador. Ver [D-027](../decisions/web-plugins.md).

Plugins 0008 fija origen de delegación y estado/tipo de eventos; no modifica ni infiere el contexto de trabajos históricos. LLM 0006 posee delegaciones/inbox con documento inmutable, claves/secuencias idempotentes y estados de recepción, redacción, entrega y descarte. 0007 reserva configuración/revisión antes de inferencia y conserva duración/fallo fijo, sin costes inventados. Presence 0016 posee época de conversación y metadatos del mensaje. Borrar incrementa la época; entregar exige coincidencia actual y confirma mediante conexión prestada mensaje, metadatos e inbox juntos. Un rollback permite reutilizar la salida lista sin otro turno. Recuperar una redacción interrumpida prepara un aviso fijo; no reenvía inferencia ni efectos. Todas estas migraciones son inmutables una vez aplicadas.

Encargos añade method/authorization opcionales al JSON, omitiendo ausencias para conservar idempotencia. method_resolution es evidencia calculada fuera del lock desde el catálogo inyectado, nunca persistida en el plan. Los hitos del constructor se leen de plugin_build_events, incluso entregados; no se alteran migraciones ni se duplica el historial.

Eliminar un encargo exige su revisión vigente y confirma la eliminación en una transacción; un conflicto no altera datos ni incrementa la revisión observada.

La migración 0002 de plugins permite encolar solicitudes independientes para el mismo plugin y conserva una única ejecución simultánea por identidad. refresh_base fija la revisión publicada al iniciar cada trabajo creado desde un encargo; al reanudar conserva la base y el candidato. 0001 permanece inmutable. Las solicitudes con distinta revisión del encargo tienen claves y chat de origen propios.

La migración 0005 de plugins añade `retry_at` UTC opcional. Un fallo transitorio confirmado del proveedor programa el siguiente intento y su aviso en la misma transacción; una cancelación lo limpia. Al reabrir se conserva el candidato y el reintento pendiente queda listo inmediatamente; trabajos sin reintento programado mantienen la recuperación anterior.
